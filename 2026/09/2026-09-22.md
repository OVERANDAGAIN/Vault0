# 消费者模型

```
你负责 SalesBench 下一阶段的“消费者模型设计与验证”。

已有 W2 调研作为起点，本轮重点是选择可用方案、完成消费者组件，并通过实际交互检查行为。请避免重新交付一份只有文献比较和待解决问题的报告。

项目背景：
我们正在开发一个多商家竞争的销售平台。消费者可以浏览商品与商家信息、查看公开排名、参与商家的公共讨论、私聊、比较和购买，也可以继续浏览或离开。消费者需要保留需求、经历和购物状态。真人和 Agent 都可能担任卖方。

UI 已由其他 Work 负责；Work3 正在评估工程基础，负责消息调度、权限、订单、资金、库存和结算。你负责消费者如何理解信息和作出行为，不要另行实现一套市场环境。

本轮请完成以下工作。

**1. 给出首版消费者的具体设计**

用一个完整例子讲清楚：同一个消费者进入市场，看到两家商家的商品与介绍，公开提问或私聊，收到回复，比较、购买或离开，之后怎样保留状态。

明确区分：

* 初始需求、偏好，以及硬性条件和可调整的期望；
* 环境提供的余额、订单等客观状态；
* 消费者已经看到的信息、形成的判断和仍不确定的问题；
* 可以采取的行为及其触发条件。

消费者只能使用自己实际看到的信息。商品真实属性、卖方宣称和消费者相信的内容需要区分，不能把卖方每句话自动当成事实。

明确说明销售难度来自哪里，例如需求匹配、价格、替代商品、尚未解决的顾虑或有限耐心。不要为了让场景“有难度”而随意增加固定拒绝率，也不要保证每位消费者最终购买。

**2. 选择实现路线，并给出推荐**

基于已有调研，比较少量最相关的路线：可直接使用的现成消费者模拟器、通用 LLM 配合需求与记忆、需要训练或微调的方案。

固定比较这些方面：
开放语言理解、多商家比较、需求与记忆保持、不购买与退出、代码或模型可获得性、调用成本、接入难度，以及已有验证证据。

先介绍候选方案原本做什么、如何产生用户行为，再解释它是否适合我们。引用优先使用原论文、官方代码和文档，区分论文描述、实际可用实现和你的推断。

给出一个首选方案和必要的简单对照。训练应由具体问题和可用数据驱动；如果建议训练，要说明训练什么、标签从哪里来、怎样判断比不训练更好。

**3. 实现一个能够独立运行的消费者组件**

完整后端尚未确定，你可以使用小型交互脚本和临时适配层。把临时接口标清楚，后续与 Work3 对齐。

组件接收个人需求、记忆、本次实际可见的消息与商品信息，以及环境返回的状态；输出公开提问、私信、继续浏览、购买请求、等待或离开等动作，并更新必要的个人记忆。

购买请求交给环境确认。消费者组件不能自行扣款、修改库存或宣布成交。收到成功、缺货、报价失效等回执后，应产生对应的后续行为。

需要展示自由语言怎样影响理解与选择，不能只读取结构化价格和属性，再用模板生成回复。

**4. 做一组小而明确的行为检查**

至少覆盖：

* 同一句介绍面对不同需求，反应是否存在合理差异；
* 补充相关信息与重复空泛宣传，是否产生不同反应；
* 两家商家各有优劣时，是否会比较，而非总选先出现的商家；
* 预算不足、需求不符或顾虑未解决时，是否能够不买或退出；
* 缺货失败、购买成功后，后续需求与状态是否正确延续；
* 面对同一设定重复运行，是否出现严重不一致。

为每项检查说明判断依据，提供实际对话和动作记录，并分析失败案例。规则一致性、对话自然度和真人行为真实性要分别讨论，不要互相替代。

在已有可用模型条件下做少量真实调用，记录模型、配置和成本。如果缺少接口或运行资源，先完成可执行脚本，并明确哪些结果尚未验证；固定回复不能冒充模型实验。

**5. 最终交付**

先用一页以内说明：

* 推荐什么消费者方案，为什么；
* 实际已经能做什么，主要不足是什么；
* 当前是否需要训练，以及下一步最值得改什么。

随后提供可运行代码、启动说明、示例配置、行为检查记录，以及给 Work3 的输入、输出、记忆与交易回执约定。注明新增依赖的安装位置和空间占用。

最终目标是拿到一个可以接入平台、行为能够检查和改进的消费者起点。消费者真实性需要继续验证，本轮不以“对话看起来像人”作为完成标准。
```
