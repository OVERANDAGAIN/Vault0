# REC-DIAL 项目架构说明

## 1. 项目在做什么

REC-DIAL 是一个用于研究**对话场景下广告推荐与插入策略**的仿真系统。

它关注的问题不是单纯“给用户推荐哪个广告”，而是在一个连续对话过程中，系统需要决定：

```text
1. 当前是否应该插入广告；
2. 如果插入广告，应该插入哪个广告；
3. 插入广告后，用户是否接受、忽略或拒绝；
4. 广告插入是否会影响用户满意度、任务完成和后续对话；
5. 如何在广告收益和用户体验之间取得平衡。
```

和传统推荐系统不同，这里不是一次性推荐，而是一个多轮交互过程。系统每一轮都要根据用户画像、历史对话、当前任务状态和候选广告，决定下一步怎么说、是否插广告，以及如何评估这一行为带来的长期影响。

可以把它理解为一个“对话式广告推荐仿真平台”：

```text
用户画像 + 用户初始需求
        ↓
系统与用户进行多轮对话
        ↓
系统在合适时机选择 topic / ad / noop 等动作
        ↓
mock user 给出反馈
        ↓
系统记录任务完成度、用户满意度、广告收益等指标
```

---

## 2. 为什么需要这个项目

传统广告推荐通常是在信息流、短视频流或网页中插入广告。系统的核心问题是：

```text
在什么时候展示广告？
展示什么广告？
展示太频繁会不会伤害用户体验？
展示太少会不会损失广告收益？
```

在对话系统中，这个问题更复杂。因为对话本身有上下文：

```text
用户正在问什么？
用户当前是否已经得到帮助？
当前话题和广告是否相关？
广告插入会不会打断用户？
用户是否已经表现出不耐烦？
```

因此，REC-DIAL 试图把广告推荐问题放到对话环境里建模，使系统不仅优化单次广告点击或接受，还考虑整个对话过程中的用户满意度、任务完成和长期收益。

---

## 3. 项目整体流程

一次完整仿真称为一个 episode。一个 episode 是一段完整对话，从用户提出初始需求开始，到任务完成、用户退出或达到最大轮数结束。

整体流程如下：

```text
Step 0: 构造用户画像和初始问题

Step 1: Monitor 观察当前对话状态
        ↓
Step 2: Planner 决定下一步动作
        ↓
Step 3: Speaker 把动作转成自然语言回复
        ↓
Step 4: Mock User 根据系统回复生成用户反馈
        ↓
Step 5: Reward Judge 评估当前轮收益和状态变化
        ↓
Step 6: 进入下一轮，直到对话结束
```

更具体地说：

```text
UserProfile + History
        ↓
Monitor
        ↓
PlannerState
        ↓
Planner
        ↓
PlannerAction
        ↓
Speaker
        ↓
AgentUtterance
        ↓
UserSimulator / Mock User
        ↓
UserResponse
        ↓
Reward / Metrics / EpisodeLog
```

其中每个模块都有明确职责。

## 4. 核心概念说明

### 4.1 UserProfile：用户画像

用户画像描述一个用户的长期属性和兴趣偏好。它通常包括：

```text
uid
demographics
persona
interests
interest_strength
preferences
intent_distribution
```

其中最重要的是：

| 字段                    | 含义                                                         |
| --------------------- | ---------------------------------------------------------- |
| `interests`           | 用户的粗粒度兴趣领域，例如 Food、Travel、Entertainment                    |
| `interest_strength`   | 用户对不同兴趣领域的强度                                               |
| `preferences`         | 来自 RealPref 的细粒度偏好记录                                       |
| `intent_distribution` | 用户更可能提出哪类任务的概率分布，例如 Recommendations、Planning and Logistics |

需要注意的是，`interests` 和 `intent_distribution` 不是同一个东西。

`interests` 表示用户喜欢什么领域：

```text
Food / Travel / Entertainment / Lifestyle / Work & Living / Social / Education
```

`intent_distribution` 表示用户更可能提出什么类型的任务：

```text
Recommendations / Planning and Logistics / Advice & Recommendations / Creative Content Generation
```

两者都和用户偏好有关，但属于不同语义空间。

---

### 4.2 Initial Query：用户初始问题

每个 episode 开始时，用户会提出一个初始问题。这个问题来自 `initial_queries.json`。

`initial_queries.json` 中每个用户都有几类初始问题候选：

```text
profile_based_queries
preference_queries
random_queries
```

它们来源不同：

#### profile_based_queries

这类 query 是根据用户的 `intent_distribution` 采样任务意图后，从 Infinite-Chats 中找对应类别的问题。

例如：

```json
{
  "query": "...",
  "source_category": "Recommendations",
  "related_categories": ["Recommendations"]
}
```

这里的 `source_category` 表示当前任务意图，例如 `Recommendations`。

#### preference_queries

这类 query 是根据用户的具体偏好生成的。

例如：

```json
{
  "query": "...",
  "source_topic": "Food: Diet",
  "preference": "..."
}
```

这里的 `source_topic` 可以直接推断当前话题，例如：

```text
Food: Diet -> Food
```

#### random_queries

这类 query 是从 Infinite-Chats 全局随机采样的。

例如：

```json
{
  "query": "...",
  "categories": ["Creative Content Generation", "Problem Solving"]
}
```

它提供的是任务类别信息，但和用户个性化兴趣的联系相对较弱。

---

### 4.3 Topic Pool：话题动作池

Topic Pool 是系统在当前 episode 中可以选择的话题候选集合。

例如用户的兴趣是：

```text
Food, Travel, Entertainment
```

那么系统可以有类似的话题动作：

```text
Food topic
Travel topic
Entertainment topic
```

Planner 可以选择某个 topic action，让系统继续围绕该话题推进对话。

Topic Pool 的合理构建很重要，因为它决定了系统除了插广告之外，还能选择哪些自然话题来继续帮助用户。

---

### 4.4 Ad Pool：广告候选池

Ad Pool 是系统可以插入的广告集合。每个广告通常包含：

```json
{
  "ad_id": "food_0",
  "brand": "Uber Eats",
  "category": "Food",
  "subcategory": "Food Delivery",
  "trigger_keywords": [
    "hungry",
    "what to eat",
    "food delivery",
    "order food"
  ],
  "target_interests": [
    "Food",
    "Lifestyle"
  ],
  "target_intents": [
    "Recommendations",
    "Advice & Recommendations"
  ],
  "reward_value": 3.0,
  "pitch_template": "..."
}
```

其中最关键的是：

| 字段                 | 含义             |
| ------------------ | -------------- |
| `category`         | 广告所属领域，例如 Food |
| `target_interests` | 适合哪些用户兴趣       |
| `target_intents`   | 适合哪些任务意图       |
| `reward_value`     | 广告被接受或点击后带来的收益 |
| `pitch_template`   | 广告话术模板         |

广告不是随意插入的，它应当和用户兴趣、当前话题、当前任务相关。

---

### 4.5 Action Space：动作空间

每一轮 Planner 都要从动作空间中选择一个动作。动作通常包括：

```text
noop: 不插广告，也不主动切换话题
topic: 选择一个话题继续推进
ad: 插入一个广告
```

可以理解为：

```text
action = -1       -> noop
action = topic_i  -> 继续某个话题
action = ad_j     -> 插入某个广告
```

动作空间由当前 episode 的 Topic Pool 和 Ad Pool 共同构成。

## 6. Runtime 架构

项目运行时的核心模块包括：

```text
SimulationRunner
DialogueEnv
Monitor
Planner
Speaker
UserSimulator / ProfileSimulator
RewardJudge
EpisodeLog / Metrics
```

它们的职责如下。

---

### 6.1 SimulationRunner：实验运行器

`SimulationRunner` 负责组织一次或多次仿真实验。

它主要做：

```text
1. 加载用户画像、初始 query、topic pool、ad pool；
2. 为每个 episode 采样用户 profile；
3. 构建该用户对应的 topic/ad 动作空间；
4. 初始化 DialogueEnv；
5. 执行 episode；
6. 保存日志和结果。
```

可以理解为实验的总调度器。

---

### 6.2 DialogueEnv：对话环境

`DialogueEnv` 是整个对话过程的环境容器。

它维护：

```text
当前用户 profile
当前对话 history
当前 episode log
当前 state
topic pool
ad pool
```

每一轮对话中，环境负责把各个模块串起来：

```text
monitor -> planner -> speaker -> user simulator -> reward -> next state
```

也就是说，`DialogueEnv` 是模块交互的中枢。

---

### 6.3 Monitor：状态监控器

Monitor 的职责是根据当前用户画像和历史对话，构造 Planner 可以使用的状态。

它输出的是 `PlannerState`。

PlannerState 应该包含：

```text
用户画像摘要
当前任务状态
当前对话历史
用户满意度估计
是否有退出意图
是否有广告抵触
当前话题
当前任务意图
```

在较简单版本中，Monitor 可以是规则模型；在较复杂版本中，Monitor 可以使用 LLM 来理解对话状态。

---

### 6.4 Planner：动作规划器

Planner 根据当前状态和动作空间选择下一步动作。

它决定：

```text
这一轮是否插广告？
如果插广告，插哪个广告？
如果不插广告，是否继续某个 topic？
是否 noop？
```

项目中可以有不同 Planner 策略，例如：

```text
noad
random
random_ad
rule
greedy_ad
conservative_ad
llm
```

不同策略对应不同的广告插入行为。

例如：

```text
greedy_ad:
    更倾向于插入高收益广告

conservative_ad:
    更谨慎，尽量在用户状态较稳定时插广告

llm:
    由 LLM 根据当前状态决定动作
```

---

### 6.5 Speaker：回复生成器

Speaker 的职责是把 Planner 选择的动作转成自然语言回复。

例如 Planner 选择：

```text
action = food_0 advertisement
```

Speaker 会生成类似：

```text
By the way, Uber Eats has a new user promo...
```

Speaker 不应该负责决定广告是否相关，也不应该负责计算用户是否会接受广告。它只负责“怎么说”。

也就是说：

```text
Planner 决定做什么；
Speaker 决定怎么表达；
UserSimulator 决定用户如何反应。
```

---

### 6.6 UserSimulator ：模拟用户

UserSimulator 是 mock user，用来模拟用户在对话中的反馈。

它需要根据：

```text
用户画像
当前满意度
当前耐心
广告敏感度
当前话题深度
广告相关性
广告曝光频率
```

生成用户反馈。

对于普通回复，用户可能继续追问、补充信息或表示满意。

对于广告回复，mock user 会判断是否接受广告、忽略广告或拒绝广告。

当前项目中的广告反应大致依赖：

```text
accept_prob
threshold
ad_relevance
patience
satisfaction
topic_depth
ad_frequency
ad_sensitivity
```

如果接受概率低于阈值，mock user 就会拒绝广告。

---

### 6.7 RewardJudge：奖励评估器

RewardJudge 用来评估当前轮动作的收益。

奖励可能包括：

```text
任务推进程度
用户满意度
对话是否应该继续
广告收益
终止信号
```

例如一次 reward 可能包含：

```json
{
  "task": 0.6,
  "satisfaction": 0.05,
  "continuation": 0.9,
  "terminal": 0.0,
  "ad_reward": 0.0
}
```

在广告推荐问题中，reward 不应只看广告收益，还要考虑任务完成和用户体验。

---

### 6.8 EpisodeLog / Metrics：日志与指标

每个 episode 会保存完整过程，包括：

```text
每一步用户说了什么
系统说了什么
Planner 选择了什么动作
是否展示广告
广告结果是什么
reward 是多少
用户满意度和耐心如何变化
是否终止
```

这些日志用于后续分析：

```text
广告曝光次数
广告接受率
广告拒绝率
平均 reward
任务完成率
用户退出率
平均对话长度
不同 planner 的对比
```

---

## 7. 一轮对话具体发生了什么

下面用一个简化例子说明。

### Step 0：初始化用户

系统采样一个用户：

```text
用户兴趣：Food, Travel, Lifestyle
任务意图分布：Recommendations 0.3, Planning and Logistics 0.15, ...
广告敏感度：0.55
初始耐心：0.8
```

用户初始 query 可能是：

```text
Can you recommend some good restaurants nearby?
```

这个 query 可能来自：

```text
source_category = Recommendations
```

因此可以得到：

```text
current_task_intent = Recommendations
```

同时可以根据用户兴趣和 mappings 推断：

```text
current_topic = Food
```

---

### Step 1：Monitor 构造状态

Monitor 读取用户画像和历史对话，构造当前状态：

```text
当前 topic = Food
当前 task intent = Recommendations
用户没有退出意图
用户满意度正常
广告曝光次数 = 0
```

---

### Step 2：Planner 选择动作

Planner 在动作空间中选择：

```text
food_0 advertisement
```

即插入 Uber Eats 广告。

---

### Step 3：Speaker 生成广告话术

Speaker 将广告动作转成自然语言：

```text
By the way, Uber Eats has a new user promo - $20 off your first order...
```

---

### Step 4：计算广告相关性

系统根据当前状态计算广告相关性。

广告 `food_0` 的 metadata 是：

```text
category = Food
target_interests = Food, Lifestyle
target_intents = Recommendations, Advice & Recommendations
```

当前用户和上下文是：

```text
profile.interests 包含 Food
current_topic = Food
current_task_intent = Recommendations
```

因此：

```text
interest_match = 1.0
topic_match = 1.0
intent_match = 1.0
```

广告相关性为：

```text
ad_relevance = 0.4 * 1.0 + 0.3 * 1.0 + 0.3 * 1.0 = 1.0
```

---

### Step 5：Mock User 判断是否接受广告

mock user 根据：

```text
ad_relevance
patience
satisfaction
topic_depth
ad_frequency
ad_sensitivity
```

计算广告接受概率。

如果接受概率高于阈值，用户可能接受或点击广告。

如果低于阈值，用户可能说：

```text
I'm not interested in ads.
```

---

### Step 6：记录 reward 和状态变化

系统记录：

```text
广告是否被接受
用户满意度是否下降
是否获得广告收益
对话是否继续
```

然后进入下一轮。

## 10. 项目中的策略配置

运行仿真时可以配置多个模块策略。

常见配置包括：

```text
monitor = rule / llm
planner = noad / random / greedy_ad / conservative_ad / llm
speaker = mock / llm
reward_judge = none / llm
user_response = rule / hybrid / llm
```

不同组合可以形成不同实验条件。

例如：

```text
monitor=llm, planner=greedy_ad, speaker=llm, reward_judge=none, user_response=hybrid
```

表示：

```text
用 LLM 理解对话状态；
用 greedy_ad 策略选择广告；
用 LLM 生成系统回复；
不使用 LLM reward judge；
用户响应使用 hybrid 模式。
```

## 15. 项目代码结构与文件职责

为了方便后续阅读代码，可以把项目代码理解为三层：

```text
第一层：数据准备与实验入口
    scripts/
    data/
    data_test/

第二层：REC-DIAL 核心逻辑
    src/recdiag/core/
    src/recdiag/env/

第三层：数据加载、处理与工具模块
    src/recdiag/data/
    src/recdiag/llm/
    src/recdiag/metrics.py
    src/recdiag/reward.py
```

整体上，`scripts/` 负责“怎么跑实验”，`src/recdiag/` 负责“实验内部怎么工作”，`data/processed/` 负责存放已经处理好的用户、query、topic、ad 等数据。

---

### 15.1 顶层目录说明

项目根目录下主要包含：

```text
recdiag/
├── data/
├── data_test/
├── docs/
├── experiments/
├── output/
├── scripts/
├── src/
└── tests/
```

各目录含义如下：

| 目录                | 作用                                               |
| ----------------- | ------------------------------------------------ |
| `data/`           | 项目主要数据目录，包含关键词、processed JSON 等                  |
| `data/processed/` | 数据预处理后的核心 JSON 文件，例如用户画像、初始 query、广告池、topic pool |
| `data_test/`      | 测试样例数据                                           |
| `docs/`           | 项目说明文档、设计文档、分析文档                                 |
| `experiments/`    | 实验配置或实验记录                                        |
| `output/`         | 仿真实验输出，例如 episode log、指标结果                       |
| `scripts/`        | 可直接运行的脚本，例如数据处理、仿真运行、结果汇总                        |
| `src/recdiag/`    | REC-DIAL 的核心 Python 包                            |
| `tests/`          | 单元测试或功能测试                                        |

---

---

### 16.2 `scripts/run_simulation.py`

这是仿真实验的主入口。

它负责真正运行一批对话仿真。通常会做：

```text
加载 processed 数据
        ↓
采样用户 profile
        ↓
构建该用户的 topic/ad 动作空间
        ↓
初始化 DialogueEnv
        ↓
执行多轮对话
        ↓
保存 episode log 和实验结果
```

如果想知道“实验是怎么跑起来的”，应该先看这个文件。

它通常会涉及：

```text
IntegratedCorpus
AdMatcher
TopicPool
DialogueEnv
Monitor
Planner
Speaker
ProfileSimulator
RewardJudge
```

可以把它理解为实验总调度器。

---

### 16.3 `scripts/check_ad_outcomes.py`

这个脚本主要用于检查广告曝光结果，例如广告是否被展示、是否被接受、是否被拒绝。

它适合用于快速回答：

```text
广告到底有没有展示？
广告展示后 outcome 是什么？
不同 planner 的广告结果有什么差异？
```

如果出现广告收益为 0，或者所有广告都 rejected，可以先用这个脚本做初步检查。

---

### 16.4 `scripts/summarize_baselines.py`

这个脚本通常用于汇总 baseline 实验结果。

它适合回答：

```text
不同 planner 策略的整体表现如何？
平均 reward 是多少？
广告曝光次数是多少？
任务完成率如何？
```

它更偏实验结果统计，不直接影响仿真逻辑。

### 20.1 `profile.py`

定义用户画像的数据结构。

```text
uid

interests

preferences
intent_distribution
```

如果想知道用户画像对象里有哪些字段，应看这个文件。

---

### 20.2 `types.py`

定义核心类型。

例如：

```text
PlannerAction
AgentUtterance
UserResponse
AdEvent
EpisodeStep
```

这些类型用于规范模块之间传递的数据。

例如：

```text
Planner 输出 PlannerAction
Speaker 输出 AgentUtterance
Mock User 输出 UserResponse
```

如果想理解不同模块之间传的对象是什么，应看这个文件。

---

### 20.3 `state.py`

定义对话状态和 planner 状态。

通常包含：

```text
BeliefState
DialogueContext
PlannerState
```

Monitor 会构造 `PlannerState`，Planner 根据这个状态选择 action。

如果想理解：

```text
Planner 能看到什么状态？
当前 topic / task intent 应该放在哪里？
用户满意度或退出意图怎么传给 Planner？
```

应看这个文件和 `monitor.py`。

---

### 20.4 `simulator_state.py`

定义 mock user 内部状态。

通常会维护：

```text
satisfaction
patience
turns_elapsed
current_topic_id
current_topic_depth
ads_seen
```

这些变量影响用户下一轮怎么反馈。

例如：

```text
用户耐心越低，越容易拒绝广告；
广告曝光越多，越容易产生抵触；
当前 topic 讨论越深入，插入相关广告可能更自然。
```

如果要理解 mock user 的内部状态如何变化，应看这个文件。

## 21. Monitor / Planner / Speaker

这三个模块是系统决策链路的核心。

---

### 21.1 `monitor.py`

Monitor 负责观察当前对话历史，并构造 PlannerState。

它的输入通常是：

```text
profile
history
episode_log
```

输出是：

```text
PlannerState
```

Monitor 需要判断：

```text
当前任务是否完成？
用户是否满意？
用户是否有退出意图？
用户是否对广告反感？
当前 topic 是什么？
当前 task intent 是什么？
```

可能有两类实现：

```text
RuleBasedMonitor
LLMBasedMonitor
```


---

### 21.2 `planner.py`

Planner 负责选择下一步动作。

它的输入是：

```text
PlannerState
ActionSpace
```

输出是：

```text
PlannerAction
```

动作类型包括：

```text
noop
topic
ad
```

不同 planner 策略会有不同选择倾向：

```text
noad:
    从不插广告

random:
    随机选择动作

greedy_ad:
    更倾向高收益广告

conservative_ad:
    更谨慎地插广告

llm:
    使用 LLM 决策动作
```

如果要分析“为什么系统这一轮选择了广告而不是话题”，应看这个文件。

---

### 21.3 `policy.py`

`policy.py` 通常包含更具体的策略实现或 planner policy 逻辑。

可以理解为 Planner 的策略细节层。

如果 `planner.py` 是统一接口，那么 `policy.py` 可能包含不同策略的内部规则。

例如：

```text
如何选择最高 reward 的广告？
如何避免过早插广告？
如何处理 noop？
如何根据当前状态过滤 action？
```

具体实现要以代码为准，但该文件通常和 action selection 直接相关。

---

### 21.4 `speaker.py`

Speaker 负责把 PlannerAction 转成自然语言回复。

例如 Planner 选择：

```text
action_type = ad
item_id = food_0
```

Speaker 会生成广告话术。

如果 Planner 选择：

```text
action_type = topic
item_id = Food
```

Speaker 会生成围绕 Food 继续对话的话术。

重要原则：

```text
Speaker 负责“怎么说”；
不应该负责“广告是否相关”；
也不应该负责“用户是否接受广告”。
```

---

## 22. 用户模拟相关模块

用户模拟模块主要位于：

```text
src/recdiag/core/simulators/
src/recdiag/core/simulator.py
src/recdiag/core/ad_reaction.py
src/recdiag/core/response_generator.py
```

---

### 22.1 `simulator.py`

定义用户模拟器的基础接口。

它规定 mock user 应该具备什么能力，例如：

```text
reset()
generate_initial_query()
generate_response()
```

其他具体 simulator 会继承或实现这个接口。

---

### 22.2 `simulators/profile_simulator.py`

这是当前最重要的 mock user 实现之一。

它根据用户画像和内部状态生成用户反馈。

它通常处理两类回复：

```text
普通对话回复
广告反馈
```

对于广告，它会进入 `_handle_ad()` 一类逻辑，根据：

```text
ad_relevance
patience
satisfaction
topic_depth
ad_frequency
ad_sensitivity
```

计算用户是否接受广告。


---

### 22.3 `simulators/rulebased.py`

规则用户模拟器。

它通常不调用 LLM，而是根据规则生成用户回复。

适合做低成本测试和 debug。

例如，当不希望消耗 LLM API 时，可以用 rule-based 或 mock 模式先跑 smoke test。


---

### 22.5 `ad_reaction.py`

负责广告反应模型。

它通常定义：

```text
AdReactionContext
AdReactionModel
```

并计算：

```text
accept_prob
engagement_score
read_ad
```

核心因素包括：

```text
topic_depth
satisfaction
patience
ad_relevance
ad_frequency
ad_sensitivity
```

如果广告被拒绝，通常可以在这个文件中找到接受概率为什么低。

例如：

```text
topic_depth 太低，说明广告插入太早；
patience 太低，说明用户已经不耐烦；
ad_relevance 不高，没有触发相关性加分；
ad_frequency 太高，广告曝光过多。
```

---

### 22.6 `response_generator.py`

负责生成用户或系统的文本回复模板。

如果用户回复出现固定模板，例如：

```text
I'm not interested in ads.
```

可能和这个文件或 `profile_simulator.py` 中的 rejection template 有关。


---

## 23. 广告插入与安全模块

### 23.1 `src/recdiag/core/ad_insertion/safety_filter.py`

该文件用于过滤不安全或不合适的内容。

在对话广告场景中，系统可能需要避免：

```text
敏感内容
不合适广告
危险建议
违反安全要求的话题
```

如果某些话题或广告被过滤，应检查这个文件。

---

### 23.2 `src/recdiag/core/relevance.py`

从文件名看，该文件用于相关性计算。

它可能包含：

```text
用户兴趣和广告的匹配
当前 topic 和广告的匹配
当前 task intent 和广告的匹配
relevance breakdown
```

如果项目中已经有该文件，优先不要新增重复模块，而应检查这个文件中是否已经存在可复用的相关性逻辑。

当前广告反馈失真的一个核心问题就是：

```text
relevance 计算需要的数据可能没有传到这里，
或者计算结果没有传到 mock user。
```

## 24. 对话环境模块：`src/recdiag/env/`

### 24.1 `env/dialogue_env.py`

这是运行时最核心的环境文件。

它负责把 Monitor、Planner、Speaker、UserSimulator、Reward 串起来。

一个典型 step 过程是：

```text
当前 history
    ↓
Monitor.build_state()
    ↓
Planner.act()
    ↓
Speaker.generate_utterance()
    ↓
UserSimulator.generate_response()
    ↓
RewardJudge.evaluate()
    ↓
更新 history 和 episode_log
```

如果想理解一轮对话到底怎么执行，应优先看这个文件。

它通常负责：

```text
reset episode
初始化 initial query
维护 history
执行 step
保存 bot/user message
触发 reward
判断 done
```

当前排查 user feedback 失真时，这个文件很关键，因为需要确认：

```text
initial query metadata 是否进入 history
current_topic/current_task_intent 是否进入 state
ad_relevance 是否在 user simulator 之前被注入
bot_metadata/user_metadata 是否写入 episode log
```

## 31. 总结

从代码结构看，REC-DIAL 可以理解为：

```text
数据层：
    负责构建用户、query、topic、广告和映射关系。

对话环境层：
    负责组织一轮轮对话，把 monitor、planner、speaker、mock user、reward 串起来。

策略层：
    负责决定什么时候插广告、插哪个广告、是否继续 topic。

用户模拟层：
    负责模拟用户对系统回复和广告的反馈。

评估层：
    负责记录 reward、广告收益、用户满意度和实验指标。
```
