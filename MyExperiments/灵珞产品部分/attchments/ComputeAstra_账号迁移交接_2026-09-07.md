## 5 双场景方案究竟在做什么

用户继续在原来的软件中工作，将一项明确、耗费算力的任务交给平台，平台在外部机器执行并返回结果。

### 需求端与供给端分工

- VS Code 插件：读取被授权的项目信息，确认运行配置，提交代码任务，展示状态、日志和结果。实际执行的是 Python 等程序，VS Code 本身不提供 GPU。
- Blender 插件：读取工程、相机、帧范围、渲染设置和素材，提交渲染并收取帧序列。用户仍负责建模和设计，远端运行 Blender 完成指定渲染。
- Local Helper：两个插件共用的本地工具，负责检查、快照、上传、下载等。默认按需运行。
- 平台后台：统一管理任务、资源占用、授权、预算、状态、结果和结算。
- Worker/执行节点：接收并实际执行任务，是供给侧执行能力。
- 安装需求端插件不意味着同意出租自己的 GPU。需求端使用、文件上传、消费和设备出租是不同授权。

### 首版限制与关键承诺

- 先做 Python/PyTorch 单机单卡评测、批推理；用户有已有项目和明确运行目标。
- 客户端首发普通 Windows/Linux 本地工作区；目标执行环境是经过测试的 Linux/NVIDIA 组合。
- 使用有限、经过测试的环境和依赖路径；Conda、自定义 CUDA 扩展、系统依赖等未经支持时需适配。
- Blender 后接，先固定版本和 Cycles，单机正确后再做可独立求值的动画帧并行。
- 文件上传齐备并由平台接管后，任务可脱离客户端持续执行。
- 不承诺任意运行中进程透明迁移，不合并跨机器显存，不自动拆解任意 Python 程序。
- 结果先独立持久保存，再释放可能删除临时数据的资源；本地下载失败不应触发整项 GPU 重跑。
- 分别记录执行、结果保存、本地回传和费用状态。进程退出成功不等于结果已交付。
- 构建、试跑、正式执行、重试等共享任务总预算。
- 成功配置保存为模板，减少重复配置。普通用户不必安装 Docker；M2 验收写明“用户无需写镜像或选机器完成支持任务”。这不等于任意项目无需整理就能运行。
- 示例的 30 元、100 元、240 帧、两个节点都是说明格式的数字，不是报价或性能承诺。
