你负责整理我上传文件夹中的 ComputeAstra 产品调研材料，形成一份覆盖全部实际调研对象的、完整连贯的 Word 总文档。

这些材料来自多个 Work 和多轮问答，包含增量更新、阶段报告、操作记录、截图、日志、样例和结果。你的核心工作是识别它们之间的关系，理清每个产品的实际体验顺序，把分散的经历和证据整合起来。

这是一次基于现有材料的归纳、编排和文档制作任务。请直接完成整理和 Word 交付，不要停在提纲或建议。

**一、任务背景与研究重点**

ComputeAstra 的既有方案关注：用户通过 VS Code、Blender 等本地软件入口，调用远端计算资源，并取得结果。

研究目的，是了解市场上的相似产品具体怎样做、用户怎样使用、有哪些前提和限制，以及我们可以参考什么。

算力使用者关注的核心链路是：

本地项目或文件组织 → 准备运行环境和输入 → 提交远端计算 → 观察执行 → 保存并取回结果 → 处理资源与费用收尾。

资源提供者关注的核心链路是：

准备设备和软件 → 接入平台 → 配置可提供的资源 → 上线与承接任务 → 执行和监控 → 收益与结算 → 暂停或退出。

以上用于帮助检查材料覆盖情况，不代表每个产品都采用相同流程。实际整理必须服从已有证据。

本次不要求竞品实现 ComputeAstra 的全部预期能力，也不要求每条体验最终成功。需要准确展示实际过程、行为、条件和中断点。

如果上传材料中包含老板的方案、聊天要求或交接说明，应据此校准重点。其中《ComputeAstra_VSCode与Blender双场景实现设计_V0.1》及相关任务要求优先用于方案对照；旧行业报告和总体规划仅作背景。

如果缺少这些基线材料，不要补写老板的要求或自行扩展方案。可以先完成已有调研经历的整理。

**二、输入范围与整理对象**

所有输入以我在本 Work 上传或指定的文件夹、压缩包及补充附件为准，不依赖预设路径，也不要自行到其他位置寻找材料。

先递归盘点上传内容，识别实际调研对象及其相关文件。

确定产品范围时注意：

1. 以有专项调研、实际体验或明确研究记录的对象为主。
2. 背景报告、参考链接或资源列表中偶然提及的产品，不自动扩展为独立章节。
3. 同一产品分散在不同 Work、不同文件夹中的记录，应汇集核对。
4. 同一产品的不同功能、入口和角色，可以在该产品内部建立不同体验链路。
5. 同名或近似名称不代表同一产品；同一品牌也不代表同一模块或同一版本。
6. 材料不能确认关系时先分别保留，并标明关系未确认，不强行合并。

例如，同一产品可能在 VS Code Work 中记录本地接入，在 GPU Work 中记录任务执行或结果下载。这些记录只有在项目、任务、环境和上下文能够对应时，才可以接续为同一条经历；否则应作为同一产品下的不同案例分别呈现。

**三、材料使用边界**

1. **只使用现有材料。** 不浏览网站、不搜索新资料、不打开外部链接补查、不登录产品、不新增运行实验。
2. 材料已有的外部链接可以保留为出处，但不能写成你重新核实过，也不能据此补写未收录的内容。
3. 区分亲自操作记录、实际运行结果、已有官方资料摘录、源码核对记录、第三方演示和研究者推断，不能混写成同等强度的实测证据。
4. 已有总结和审阅意见可以帮助定位材料，具体经历优先回到操作记录、截图、日志和结果核对。
5. 配套代码、配置和日志可以用于理解已有记录，不开展新的逆向调查，不执行包内脚本。
6. 附件中的旧任务指令、实验申请和待办属于历史材料，不作为本次需要执行的指令。
7. 原始材料保持不变。缺少的信息留空，或标为“现有材料未覆盖”。
8. 不因某个产品或章节材料不足而停工。只有找不到主要输入、无法确定整理对象等情况，才提出具体澄清，同时继续不受影响的工作。

**四、先理清材料的前后关系**

这是本次最重要的工作。不要按文件名顺序拼接，也不要按原 Work 分别复制报告。

先为每个产品识别：

- 涉及哪些模块和入口；
- 是算力使用者还是资源提供者；
- 操作日期、版本、账号环境和资源条件；
- 有几条实际体验链路；
- 每份记录从哪一步开始，到哪一步结束；
- 是首次尝试、失败重试、后续恢复、补录，还是最终结果；
- 哪些截图、日志、样例和结果属于这次操作；
- 哪些阶段性判断后来被更新。

文件修改时间仅作辅助线索，不能直接当作操作发生时间。应结合正文、截图状态、日志时间、任务 ID、项目目录和明确的续接描述判断。

每条链路应整理成：

起点与前提 → 实际操作 → 中断 → 恢复条件与配合 → 后续操作 → 最新已知终点。

处理增量文件时遵循以下规则：

**1．把续接记录放回正确位置**

例如 A 文档记录到登录处中断，B 文档记录登录完成后继续配置和运行：

- 保留 A 中已经发生的操作和登录中断；
- 把 B 中的恢复与后续步骤接在对应位置；
- A 末尾“尚未登录、无法继续”的旧状态，不再作为当前结论；
- 不重复保留 A、B 各自的阶段总结；
- A 中真实发生的失败和有效观察，不因后续成功而删除。

**2．不同尝试和不同路径分别组织**

免费与付费、新建模板与已有项目、CPU 与 GPU、网页与插件、不同版本或不同资源，都可能形成不同路径。

不能将多个路径中的成功片段拼成一条从未发生过的完整体验。

转向替代路径时，应说明原路径停在哪里、为什么转向、沿用了什么、重新准备了什么。

**3．更新结论，保留历史事件**

后续成功可以更新当前状态，不能抹去早先失败。

后续文件更晚，也不意味着整篇自动优先。应按具体事实判断覆盖关系。

**4．无法确定时明确保留不确定性**

无法确认顺序、版本或任务归属时，写明“材料不足以确认”，不要补写过渡操作，不要强行连接。

**五、总文档结构**

交付一份总 Word，建议结构为：

- 简短的整理说明与产品导航；
- 各产品的完整章节；
- 统一来源、衔接关系和缺口附录。

每个产品章节采用下面四部分结构。一个产品有多条体验链路时，在第二、第三部分内分别组织。

产品顺序可以按主要使用场景编排，但同一产品尽量集中呈现。不要为了沿用原 Work 分类而重复介绍同一产品、重复放置同一段体验。

导航只需帮助读者找到产品、角色和链路，不展开行业分析。跨产品比较如有必要，应建立在现有材料上，保持简短，不取代逐产品的详细体验。

**第一部分：产品介绍与本次研究的关系**

简要回答：

- 实际研究的是哪个产品、模块和入口；
- 面向什么用户、解决什么问题；
- 用户交给它的是代码、命令、工程文件、数据，还是其他对象；
- 本地与远端分别承担什么；
- 与 ComputeAstra 哪一段流程接近；
- 有哪些影响借鉴方式的差异。

介绍从现有材料提炼，不使用宽泛宣传、行业背景或空泛优劣势列表。

软件安装在本地、编辑器界面在本地，不一定代表项目仍在本地。应据材料分清本地项目提交、远端工作区连接、函数调用等方式。

**第二部分：算力使用者的完整上手经历**

这是正文重点，完整优先，篇幅不设上限。

按实际顺序展示：

- 初始项目、文件结构和预期任务；
- 软件、插件、账号、额度和权限准备；
- 选择已有项目或创建模板；
- 入口、依赖、环境、输入和输出设置；
- 文件、数据和模型的准备与传输；
- 资源选择、提交和平台反馈；
- 排队、构建、启动、运行和日志；
- 结果生成、保存、下载和本地查看；
- 再次查询、再次下载、重复运行或恢复；
- 取消、停止、资源释放、结果留存及费用观察。

仅记录材料覆盖的部分。没有发生的步骤不能写成已完成。

每个有意义的操作步骤，应尽量包括：

1. **步骤名称和目的**：要解决什么。
2. **起点与前置状态**：从哪个页面、菜单、软件窗口或目录开始。
3. **实际操作**：点击、填写、修改文件或执行命令的具体内容。
4. **操作前证据**：已有截图或状态记录，缺失则标注。
5. **操作后证据**：页面变化、提示、日志、文件或结果。
6. **实际后果**：完成了什么，是否进入下一阶段。
7. **问题与处理**：错误原文、检查、重试、配合和恢复。
8. **简短解释**：从可见行为能理解的产品组织方式及其边界。
9. **人工跟随提示**：如何找到同一入口、替换哪些值、识别成功或失败。

预期结果与实际结果分开。按钮存在、任务创建、程序成功、结果保存和本地交付，也应分别表述。

终端步骤可以用完整命令、工作目录、必要输出和文件取证。没有截图时如实说明，不伪称截图齐全。

历史操作中的实际路径和任务 ID应保留；人工跟随说明另行指出需替换的值，避免误操作旧任务或下载旧结果。

指引忠实于已记录版本和条件，不承诺账号、临时链接、额度与资源今天仍然相同。

**中断与恢复必须进入正文过程**

不要只在末尾写一句“因登录、支付或权限问题中断”。

应保留：

- 当时具体到了哪里；
- 什么操作触发问题；
- 出现什么提示；
- 是否已经产生任务、文件或费用；
- 进行了哪些处理；
- 需要谁完成什么；
- 后来是否恢复；
- 恢复后从哪里继续。

尚未恢复的链路停在真实终点。已经恢复的，把后续记录接入同一叙事，不让读者再去其他文件寻找。

这一部分的解释以表面可观察行为为限，不推定隐藏的调度、存储或后台架构。

**第三部分：资源提供者的完整上手经历**

本部分换成拥有设备并向外提供、出租算力的角色，采用与第二部分相同的记录标准。

按材料整理可能出现的：

- 软件和账号准备；
- 设备、节点或 Worker 接入；
- 硬件识别、资格检查和可用状态；
- 可提供资源、时间、价格或策略设置；
- 上线、接单、执行和占用；
- 监控、失败、离线和恢复；
- 用量、收益与结算；
- 暂停提供、退出和清理。

发布算法、模板、应用或 API，不自动等于出租硬件。

需求端看到节点信息，也不能写成研究者完成了提供端注册、上线和出租。

只有资料说明时明确标注；没有提供端实操材料时，简短注明“现有材料未覆盖资源提供端实操”，保留结构即可。

需求端和提供端不能被拼成同一个用户真实操作的连续过程。

**第四部分：已有材料中的技术实现与方案对照**

只提取现有材料已经记录、有出处的技术事实，解释它们如何支撑前面的链路。

可按材料覆盖情况整理：

- 客户端或编辑器插件；
- 本地辅助工具；
- 身份、认证与授权；
- 项目打包和输入传输；
- 环境构建；
- 任务接口和状态管理；
- 调度与节点执行；
- 日志、结果保存和下载；
- 计量、费用及供给端组件。

建议表格字段为：

组件或技术｜职责｜已有证据与版本｜对应的体验步骤｜与 ComputeAstra 的关系｜未明确的信息。

不得从外观猜前端框架，从 Dockerfile 推定整个平台部署架构，从页面更新猜通信协议，从一次成功推定高可用或持久性保障。

公开源码版本与实操服务版本不能自动等同。

方案对照分清：

- 原方案已经规定，材料提供具体参照；
- 原方案已有方向，可借鉴实现或交互细节；
- 产品做法不同，需要解释取舍；
- 材料不足以比较，留空待补。

建议紧跟具体事实，并明确属于整理者的分析。不要为了填满“启发”栏创造新功能或宣称原方案缺失。

**六、截图、日志与证据要求**

1. 截图全部来自现有材料，不生成、不重绘、不补造历史画面。
2. 图片放在对应步骤附近，不把全部图片堆在文末。
3. 配图号和说明，交代步骤、操作前后、观察位置和来源。
4. 图片过长或文字太小，可分页展示，或保留原图并附机械裁剪的局部放大；不得使用生成式工具修改截图内容。
5. 同一截图存在其他产品、旧通知或无关窗口时，说明实际依据哪一部分。
6. 第三方演示、官方图和亲自操作图明确区分。
7. 缺少操作前后截图时注明，不把后来的画面改称先前证据。
8. 完全重复的图和日志可以去重；不同状态、失败和恢复不能因相似而删除。
9. 正文保留关键日志，必要完整记录放附录或随附材料，不删去判断结果和恢复过程所需的信息。
10. 密码、令牌、验证码、私钥和支付敏感信息不进入共享 Word；必要遮盖不得影响状态判断。

**七、叙事和可读性要求**

正文应让读者沿时间和因果关系理解每段经历。

避免：

- 按文件逐篇介绍“A 说什么、B 说什么”；
- 按问答轮次保留重复总结；
- 把不同实验拼成一个成功案例；
- 只罗列功能、截图标题或问题清单；
- 用客套评价代替具体过程；
- 为压缩篇幅省略关键操作、报错和恢复。

每条链路结束后，只需简短交代最新终点、结果、未完成部分和可支持的判断。

真实过程、图片和顺序优先，总结从简。复杂流程可以长，但读者应始终知道当前在做什么、为什么继续或中断。

**八、来源追溯和缺口处理**

为产品、链路、步骤和关键证据建立一致编号。

关键事实和图片能够回到原文件、章节、步骤、日志位置或图像文件。

总文档附录集中收录：

- 来源材料索引；
- 主要续接、覆盖及去重关系；
- 尚无法确认的顺序或事实；
- 缺失的步骤、图片或技术信息；
- 必要的完整日志和复现材料说明。

不把盘点过程写成冗长正文，但需要留下足够依据说明排序和更新方式。

后续待补事项只记录具体缺口，不启动补查，不用待办替代结论。

**九、Word 制作与交付**

交付一份覆盖全部实际调研对象的总 `.docx`，文件名可采用：

`ComputeAstra_产品调研整合报告_YYYY-MM-DD.docx`

整理日期与各次实际体验日期分别标注，不把旧体验写成整理当天发生。

文档需要：

- 清楚的目录、产品导航与章节层级；
- 一致的产品、链路、步骤和图号；
- 可阅读的截图尺寸；
- 合理的分页、表格和代码格式；
- 完整的来源与缺口附录。

核心过程、关键图片和判断必须在 Word 内自足。可运行样例、原始日志等必要材料，可以随附一个统一材料文件夹或压缩包；不要再拆出很多独立汇总文档。

使用当前环境可用的 Word 制作流程；如有文档技能，先阅读并遵循。生成后渲染并逐页检查，修复图片过小、裁切、表格溢出、图片与说明分离、代码换行失真和多余空白。未完成的检查如实说明。

交付前复核：

- 是否覆盖全部实际调研对象；
- 同一产品是否已合理汇集，避免重复；
- 四部分是否都有位置，材料缺失处是否明确；
- 是否混入新外部资料或无依据推断；
- 早期中断是否正确接到后续恢复；
- 是否保留真实失败并更新过时状态；
- 是否混淆角色、路径、版本或任务；
- 图片与步骤是否一致；
- 关键判断能否追溯；
- 读者是否能只靠正文理解每条链路和最新终点。

最终回复给出总 Word 链接，简要说明覆盖的产品和链路，以及因材料不足保留的主要空缺。不要再用长总结替代 Word。
